# ADR-0008: Tracing

Status: accepted, 2026-11-13

The platform emits traces through the OpenTelemetry API (`opentelemetry-api>=1.45`, Apache-2.0) and depends on nothing else for tracing. The API package is a set of interfaces that do nothing until a process installs an SDK and an exporter, so a library user, the test suite and the benchmark pay no cost and need no collector; the SDK (`opentelemetry-sdk`) is a development dependency, used by tests through its in-memory exporter and by the run command when an exporter is configured. Model-call spans follow the OpenTelemetry generative AI conventions (`gen_ai.operation.name`, `gen_ai.request.model`, `gen_ai.usage.input_tokens` and the rest), so any viewer that reads them (Phoenix, Langfuse, a general tracing backend) shows tokens and models without a mapping. Cost: those conventions are at Development status and were moved to their own repository in 2026, so attribute names may change without a deprecation period; they are written in one module, and the conventions carry no cost attribute, so cost is recorded under the project's own name. Alternatives considered: a vendor SDK such as LangSmith or Langfuse's own client (ties the platform to one backend and one account); a table of spans in Postgres with a custom viewer (a trace viewer is not what this project is about); structured logs only (no parent-child timing, which is the point of looking at a multi-step run).
