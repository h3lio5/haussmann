# ADR-0011: Trace export and viewer

Status: accepted, 2026-11-14

To look at a run's trace, the demo command can send its spans over OTLP/HTTP (`opentelemetry-exporter-otlp-proto-http>=1.45`, Apache-2.0, a development dependency) to Jaeger (`jaegertracing/jaeger:2.23.0`, Apache-2.0), which `compose.yaml` starts under the `traces` profile. The platform still depends only on the OpenTelemetry API (ADR-0008): the SDK and the exporter are imported inside one function of the workload's demo command, and only when `--traces` is given, so a library user, the tests and the benchmark are unchanged. OTLP is the protocol every tracing backend accepts, so the viewer can be replaced without touching code. Jaeger is one container with no account and no storage to configure; it shows the generative-AI attributes of a model call as plain tags and does not render them as a conversation. Cost: traces are kept in the container's memory and are lost when it stops, which is right for looking at one run and wrong for monitoring. Alternatives considered: Phoenix or Langfuse (they render model calls better; Langfuse needs its own database and Phoenix adds a second Python service, more than a view of one run needs); the gRPC exporter (pulls in grpcio for no gain on a local connection); the console exporter (no parent-child view, which is the point).
