# M2 plan: the engine

Status: approved 2026-11-11.

M2 builds the system that M1's benchmark was made to grade: files in, verified facts with citations in a ledger, a memo out. It is done when the engine beats both baselines on the dev scenarios on the same model, with every change logged in `EXPERIMENTS.md`.

## Where M1 left the bar

Both baselines: recall 88 %, traps 62 % (45 of 72). They never recompute a total (0 of 9), never flag a contradiction with both sources (0 of 9), and miss most expired dates (3 of 9). Those three are the first targets.

## Approach

**Thin engine first, depth second.** Slice C gets a minimal engine through the benchmark as early as possible, so every later piece is justified by a measured change. Slice D adds the memo. Slice E adds durability and tracing.

```
files ──> ingest ──> elements ──> fact-finders ──> candidate facts ──> verify ──> resolve ──> compute
          (C1)                    (C3, C4, C5)        (ledger, C2)      (C6)       (C7)       (C7)
                                                                                     │
                              benchmark Submission (C8) <── ledger state ────────────┤
                                                 memo (D1 to D3) <───────────────────┘
```

## Slice C: thin engine through the benchmark

| ID | Task | In | Out | Done when |
|---|---|---|---|---|
| C1 | Ingest (`docparse`) | a folder of files | `Element(doc_id, locator, text)` per page, sheet or email; a `DocumentCard(type, date, authority)` per file | the M1 reading step is replaced by it with identical text; cards correct on both scenarios |
| C2 | Ledger (`ledger`) | transactions of facts, citations, conflicts | append-only store; current view of facts by key and status | invariants hold under property tests; in memory for this slice |
| C3 | Tool loop (`llmkit`) | a request, tools, a turn and token budget | final answer plus a transcript of tool calls | stops on answer, on budget and on a repeated call; runs on recordings |
| C4 | Context assembler (`ctxkit`) | instructions, task, fact schema, retrieved elements, a token budget | an ordered context and a manifest of what went in | never exceeds the budget; same inputs give the same context |
| C5 | Fact-finders (workload) | fact groups from the spec, tools `search` and `read` | candidate facts with citations written to the ledger; open questions | each group runs in its own context; nothing is carried between groups except the ledger |
| C6 | Verifier, citation check | candidate facts and elements | status per fact: verified, conflict, unverified, missing; recomputed totals | a value not present at its cited locator is rejected; a total that differs from its parts is flagged |
| C7 | Resolve and compute | conflicts; verified facts | one fact per key by authority, then date, else escalation; calculator outputs | policy is code, tested on the planted contradictions |
| C8 | Engine as a contestant | ledger state | `Submission` | scored by the M1 runner next to the baselines; row in `EXPERIMENTS.md` |
| C9 | One large dev scenario | a spec of several hundred pages | files and manifest | baseline (a) no longer fits one prompt comfortably and baseline (b) keeps under a quarter of the pages |

## Slice D: the memo

| ID | Task | In | Out | Done when |
|---|---|---|---|---|
| D1 | Deliverable spec (`buildkit`) | a data file | sections, the facts each needs, calculations | the workload's feasibility memo is declared as data |
| D2 | Target hashing (`buildkit`) | spec version, input fact versions, prompt version, model id | a hash per section | changing one fact changes only the sections that use it |
| D3 | Writer | bound facts for a section | prose with placeholders bound to fact ids; conflict and open-question sections from ledger state | no number in the prose that is not a bound fact |

## Slice E: operations

| ID | Task | Done when |
|---|---|---|
| E1 | Postgres ledger and durable runner (`flow`) | the Postgres ledger passes the same contract test as the in-memory one; a run killed mid-way resumes without repeating a paid call |
| E2 | Traces and cost | each step emits an OpenTelemetry span; cost per run and per step is reported; a spend cap stops a run |

## Decisions to make in design notes

- **Where the verifier lives.** It needs both elements and facts, and `docparse` and `ledger` may not import each other. It goes in a module of the layer above; the boundaries note is revised with it.
- **PDF parsing library.** The architecture file names PyMuPDF, which is AGPL. M1 used pypdf. The parsing ADR decides.
- **Postgres driver** for the ledger and the runner: one ADR.
- **How the fact-finder searches.** Keyword, embeddings or both, measured on the large scenario and not assumed.

## Rules for this milestone

- Every change to a prompt, to context assembly, to retrieval or to the model reruns the benchmark and adds a row to `EXPERIMENTS.md`.
- A design note with each core module, as in M1.
- Held-out scenarios are not written until the engine is frozen.

## Live model cost

Mistral Small 4 through the provider-neutral client. A fact-finding run is estimated at about 250,000 input tokens per scenario (ten groups, five turns each), so about 0.04 USD per scenario run. With two to three scenarios, three samples and about ten logged experiments, the milestone is estimated at 3 to 5 USD in total, and no single run above 0.50 USD. The estimate is replaced by measured cost after the first engine run.

## Exit criteria

All gates green; the engine scored on all dev scenarios with three samples; more traps passed than both baselines, reported by type, with what still fails stated plainly; cost and latency per run reported next to the baselines.
