# M3 plan: first release

M3 turns the engine into something a reader can try: an expert opens a memo, clicks a sentence to see its evidence, corrects a fact, sees what was rebuilt, and that correction becomes a test the system must keep passing. It ends with held-out results and a README that shows them.

## Where M2 left things

A run produces a ledger and a memo, stored in Postgres and resumable. Each sentence of the memo names the facts it uses and each fact its citations (`memo.json`). Nothing yet lets a person change a fact, and every score so far is on dev scenarios.

## Order of work

The items that may never be cut come first: evidence click, edit to rebuild to diff, held-out results.

```
F  review core (no UI) ──> G  API and screen ──> I  release
H  held-out scenarios (needs the engine frozen; runs beside F and G)
```

## Slice F: review core (`review`, no UI)

| ID | Task | In | Out | Done when |
|---|---|---|---|---|
| F1 | Expert edit | a key, a value, a reason, an author | a ledger transaction: a fact with method `expert`, and the settling order becomes expert, computed, authority, date | an edited fact wins over every other source and the losing facts stay in the ledger; property test |
| F2 | Rebuild and diff | the ledger after an edit | the memo rebuilt through the runner; a diff by fact (old and new value) and by sentence, per section | one edited fact rewrites only the sections that use it, measured through a real ledger edit this time, not a changed digest |
| F3 | Review state | approve, request changes, comment, per section | state per section: draft, in review, changes requested, approved; a memo is approved when every section is | transitions tested; an edit returns its sections to in review |
| F4 | An edit becomes a regression case | an expert edit on a run | a case file: run inputs, key, expected value | `evalkit` replays the engine on the recordings and fails if a case's key no longer settles on the expected value; the gate runs in CI |
| F5 | Comment to the agent | a comment on a section | a proposed rewrite of that section, as a diff to accept or refuse | the proposal passes the writer's checks (no typed number, every fact stated) or is refused; nothing changes until accepted |

Everything in F is testable without a browser and without a live model, except F5's first recording.

### State of slice F (2026-11-14)

F1 to F5 are implemented and tested on scripted models and on recordings; design in `docs/notes/review.md`. The regression gate holds three cases: two held, one open (the owner on one small scenario). What is left is the measurement of an edit and a comment on a real memo, `python -m feasibility_fr.benchmark.review --live`, which needs two new model calls.

Expected outcome of that run, stated before it: the expert's value for the owner rewrites two sections of eight, the site section by one model call and the open questions by code; every other approval stays valid; no digit is typed by the model; the rebuild costs under 0.001 USD. The proposal made in answer to the comment either holds the writer's rules and is accepted, or is refused and changes nothing; which of the two is not predicted.

Outcome (E015): as expected on every line: 2 of 8 sections, one call, 0.00011 USD, 6 of 8 approvals kept, no digit typed; the proposal held and was accepted. Not expected: two sentences about unchanged facts were reworded in the rewritten section (`docs/notes/review.md`).

G1 to G5 are built. The evals view (G4) shows the report's tables by split, the regression cases and the experiment log, read from the committed files. It is a table, as planned first; scores by commit are not plotted (`docs/notes/review-screen.md`).

## Slice H: held-out scenarios

| ID | Task | Done when |
|---|---|---|
| H1 | Freeze the engine | a tag on the commit; no engine change after it without a new row and a stated reason |
| H2 | Two held-out scenarios | new sites, new document templates and wording, written after the freeze; the runner already refuses them without a flag |
| H3 | One run, reported separately | a row in `EXPERIMENTS.md` and a held-out table in the report, baselines and engine; whatever the result |

Held-out results are never used to change the engine. If they are bad, that is what the README says.

### Outcome of slice H (E016, 2026-11-14)

Rules and prediction were committed before the scenarios, and the scenarios before the run (`docs/notes/heldout.md`). On held-out the engine passes 85% of traps (61/72) against 74% for both baselines, and its recall is 88% (103/117) against 97% and 99%. One scenario of the two is complete; on the other the engine recorded values from documents about another lot and missed two limits of the regulation. The dev results overstate the engine's recall advantage; the README reports both splits and says so.

## Proposed cuts from the M3 list in `PROJECT.md`

These are in the project's M3 list and I propose to move them after the release, each as its own follow-up with a measured result. The decision is the owner's.

| Item | Why it can wait |

| A hosted demo | G5 makes the demo run from recordings locally; hosting it is a deployment choice to make with the README. |

Not cut: evidence click, edit to rebuild to diff, comment to agent, the regression gate in CI, held-out results, the experiment log.

## Decisions for design notes and ADRs

- **How an expert's value outranks the others** without deleting them: a method on the fact, and one more rung in the settling order.
- **What identifies a sentence** across rebuilds, so that a comment or an approval stays attached: the section and the facts the sentence uses, not its position.
- **Web framework and front-end stack**: one ADR each. The architecture file names FastAPI, React, Vite and PDF.js.
- **Where the review state is stored**: Postgres tables next to the journal, or records in the ledger.

Design notes before code, as before: `docs/notes/review.md` for F, `docs/notes/review-api.md` for G1, one note for the screen.
